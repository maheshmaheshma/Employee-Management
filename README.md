# Employee Management REST API — Phase 8

A Java 17 / Spring Boot 3 REST API for managing employee records. It follows Controller → Service → Repository layering and stores data in a thread-safe in-memory repository, so Phase 9 can replace the repository implementation with JPA/PostgreSQL without changing the controller or service contract.

## Requirements

- JDK 17+
- Maven 3.9+ (or use `./mvnw` after adding the Maven Wrapper)
- Internet access for Maven dependency downloads

## Run locally

```bash
mvn clean test
mvn spring-boot:run
```

Base URL: `http://localhost:8080`

Swagger UI: `http://localhost:8080/swagger-ui.html`  
OpenAPI JSON: `http://localhost:8080/v3/api-docs`

The repository is in memory: all records are lost when the application stops/restarts.

## Architecture

```text
controller/  HTTP endpoints and HTTP status codes
    ↓
service/     business rules, filtering, sorting, duplicate email, salary cap
    ↓
repository/  interface + ConcurrentHashMap implementation
    ↓
model/       Employee, Department, Status
```

DTOs keep the internal model separate from API contracts. Constructor injection is used throughout.

## Endpoints

| Method | Endpoint | Purpose | Success |
|---|---|---|---|
| POST | `/api/v1/employees` | Create employee | 201 |
| GET | `/api/v1/employees` | List, filter and sort | 200 |
| GET | `/api/v1/employees/{id}` | Get employee | 200 |
| PUT | `/api/v1/employees/{id}` | Full update | 200 |
| PATCH | `/api/v1/employees/{id}/status` | Activate/deactivate | 200 |
| DELETE | `/api/v1/employees/{id}` | Permanent delete | 204 |
| GET | `/api/v1/employees/search?keyword=mahesh` | Search first name, last name, email | 200 |
| GET | `/api/v1/employees/department/{dept}` | Filter by department | 200 |
| GET | `/api/v1/employees/stats` | Total headcount, department headcount, average salary | 200 |

Supported departments: `HR`, `IT`, `FINANCE`, `SALES`, `OPERATIONS`.  
Statuses: `ACTIVE`, `INACTIVE`.

List filters and sorting:

```http
GET /api/v1/employees?department=IT&status=ACTIVE&sortBy=salary&order=desc
```

Allowed sort fields: `id`, `firstName`, `lastName`, `email`, `salary`, `dateOfJoining`, `department`. `order` must be `asc` or `desc`.

## Sample request

```json
{
  "firstName": "Mahesh",
  "lastName": "Mamidi",
  "email": "mahesh@example.com",
  "phone": "9876543210",
  "department": "IT",
  "designation": "Junior Software Engineer",
  "salary": 45000.00,
  "dateOfJoining": "2025-06-15"
}
```

The `id` is generated by the repository and `status` defaults to `ACTIVE`. Email is normalized to lowercase and must be unique. Salary must be positive and cannot exceed `app.max-salary`. Date of joining cannot be in the future.

## Error format

```json
{
  "timestamp": "2026-10-06T10:15:30",
  "status": 404,
  "error": "Not Found",
  "message": "Employee not found with id 15",
  "path": "/api/v1/employees/15",
  "fieldErrors": []
}
```

Validation errors use HTTP 400 and include `fieldErrors`, each with `field` and `message`. Duplicate email uses HTTP 409. Missing employees use HTTP 404. Unexpected server errors return a generic message rather than exposing internals.

## Configuration

`src/main/resources/application.yml` defines the port, application name, default department, maximum salary, logging levels and Swagger path. Override values with Spring's standard external configuration mechanisms, for example:

```bash
SERVER_PORT=8081 APP_MAX_SALARY=2500000 mvn spring-boot:run
```

## Production-readiness notes

This assignment intentionally uses in-memory storage, so it is not durable across restarts. The repository's email uniqueness check is suitable for this learning exercise but is not atomic under concurrent create requests; a persistent database phase should enforce a unique email constraint. For production deployment, add persistence, authentication/authorization, pagination, health checks, request IDs, and deployment-specific configuration.
